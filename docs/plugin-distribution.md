# BioNexus plugin distribution guide

Updated 2026-08-31 against the current OpenAI and Anthropic documentation.

## Distribution status

BioNexus can be distributed today through two repository marketplaces and can
be submitted to both vendors' official public review flows.

| Channel | Artifact | Current path |
|---|---|---|
| OpenAI repo/workspace marketplace | `.agents/plugins/marketplace.json` + `.codex-plugin/plugin.json` | Add the GitHub marketplace, test in ChatGPT/Codex, optionally publish within a workspace |
| OpenAI universal public Plugins Directory | skills-only submission bundle | Submit through the OpenAI Platform plugin portal; approval and publisher action are required before publication |
| Claude Code self-hosted marketplace | `.claude-plugin/marketplace.json` + `.claude-plugin/plugin.json` | Add `HERRY423/BioNexus`, then install `bionexus-reliability@bionexus-marketplace` |
| Anthropic official marketplace | Claude plugin submission | Submit through the Claude.ai or Console plugin submission form; review is required |

OpenAI's public directory now accepts skills-only plugins. This replaces the
older assumption that a pure `.codex-plugin` package could only be distributed
through GitHub/workspace marketplaces. The universal OpenAI listing is shared
by supported ChatGPT and Codex surfaces, while local and repo marketplaces
remain separate authoring and private/team distribution mechanisms.

## Why the marketplace files are different

The canonical registry compiles semantic metadata into host-specific JSON:

- OpenAI repo marketplaces use a typed local source:

  ```json
  {
    "source": {
      "source": "local",
      "path": "./plugins/bionexus"
    }
  }
  ```

- Claude Code uses a repository-relative plugin source:

  ```json
  {
    "source": "./"
  }
  ```

The source forms must not be generated by one shared serializer. BioNexus uses
one semantic registry but distinct OpenAI and Claude marketplace adapters.

The OpenAI manifest is currently skills-only. It intentionally does not point
to the empty `.mcp.json`. The local BioNexus stdio MCP remains available for
explicit local setup, but a local stdio server is not being presented as a
public remote MCP submission.

## Five-minute installation

### ChatGPT / Codex from GitHub

```bash
codex plugin marketplace add HERRY423/BioNexus --ref main
```

Restart the ChatGPT desktop app, open the Plugins Directory, choose
**BioNexus Marketplace**, and install **BioNexus**. The Codex marketplace CLI
adds and tracks the source; installation and local testing occur in the
desktop plugin UI.

For reproducible institutional rollout, replace `main` with a reviewed release
tag. Do not treat a successful catalog import as proof that scientific
dependencies, local MCP execution, or any external evidence track is ready.

### Claude Code from GitHub

```bash
claude plugin marketplace add HERRY423/BioNexus
claude plugin install bionexus-reliability@bionexus-marketplace
```

Verify the marketplace from a clone before publishing:

```bash
claude plugin validate .
```

### First prompt

```text
Use BioNexus to audit this analysis. Identify the experimental unit, test the
assumptions and provenance, separate technical results from biological claims,
state the maximum warranted claim, and abstain on every unsupported field.
```

Plugin installation alone does not require installation of the full scientific
Python stack. Running local analyses, `scripts/doctor.py`, or the local MCP
server requires Python 3.10+ and the dependencies for the selected workflow.

## OpenAI public submission checklist

1. Use an OpenAI Platform organization role with Apps Management write access.
2. Complete individual or business developer-identity verification.
3. Choose **Skills only** in the plugin submission portal.
4. Upload the final skill bundle using the same file tree tested locally.
5. Supply production listing metadata, publisher/support/privacy/terms URLs,
   a logo, starter prompts, countries/regions, and release notes.
6. Provide at least five positive and three negative test cases with expected
   behavior. Negative cases should exercise refusal, missing provenance,
   unsupported claims, and unavailable scientific dependencies.
7. Review every skill for bundled scripts/assets, scoped permissions, no
   secrets, and provider-neutral instructions where the workflow is not
   OpenAI-specific.
8. Submit for review. Submission is not publication. After approval, the
   verified publisher chooses when to publish.

Public review should be for the skills-only reliability layer. Do not attach
the local stdio MCP as if it were a public production HTTP service.

## Anthropic official submission checklist

1. Run `claude plugin validate .` from a clean release checkout.
2. Test installation from the GitHub marketplace in a fresh Claude Code cache.
3. Confirm `.claude-plugin/marketplace.json` resolves `"source": "./"` from
   the repository root.
4. Confirm the plugin identifier is
   `bionexus-reliability@bionexus-marketplace` and all skill-relative files are
   inside the plugin root.
5. Submit through one of Anthropic's official in-app forms:
   - <https://claude.ai/settings/plugins/submit>
   - <https://platform.claude.com/plugins/submit>
6. Treat acceptance into the official marketplace as distribution approval,
   not scientific validation, external endorsement, or certification.

## Repository release gate

Before either public submission:

```bash
python scripts/registry_compiler.py --check
python -m pytest -q tests/unit/test_registry_compiler.py
python scripts/doctor.py
```

Also run the full applicable test/CI matrix from a clean release commit, verify
the installation in a fresh host session, and record any unavailable external
or scientific checks explicitly. A manifest validation pass proves packaging
syntax, not runtime readiness or scientific warrant.

Because the flagship verifier binds reports to a source snapshot, a source
change intentionally makes that verifier fail until provenance is reconciled.
Commit the source change first, run `python scripts/sync_flagship_reports.py`,
verify the rebound reports, and commit that provenance-only update separately.
Never label an uncommitted/dirty rebind as a clean executed validation run.
